## 验证方式

`npm test` 覆盖人口一致性、模拟再现、配置与凭证、运行 API、真实 SDK 协议、取消、独立浏览器 Gate 和完整编排。

`npm run build` 执行 TypeScript 检查与前端生产构建。

`npm run test:e2e` 从实际页面操作 Agent 复制/配置、模式选择、任务提交、交付页交互、调研展示与刷新，使用独立临时数据目录，不消费真实模型配额。

真实 SDK 的模型服务端使用本地 SSE 替身；真实 Chromium 执行生成/模板页面。这证明软件闭环和协议，不证明真实厂商模型完成需求的能力。用户尚未配置真实服务 Key，真实模型质量与成功率仍待实测。

## 下一次最有价值的工作

优先完善业务研究闭环（不再把“多生成一些居民回答”当数据补全）：

1. 数据导入向导：接受用户有权提供的匿名汇总订单、学校/候选点与试售数据，自动核对期间、单位、缺失、重复和覆盖偏差；当前仅支持人口JSON预检。
2. 场景化调研框：家长/学生分离，养宠户/宠物/客户/订单分离，明确零食与主粮；针对真实输入重新判定needs-data。
3. 空间评估：已验证边界、学校/POI、候选地址、步行或履约可达性、租金、竞争和时段客流，随后才计算可解释候选排序，不以街道总人口代替选址。
4. 同规格价格试验、SKU/猫狗分组、复购与毛利，处理促销/缺货/渠道选择偏差；由真人/业务留出集检验，不以模型自洽证明有效。
5. 数据包版本发布与城市切换、来源失效提醒、人口和业务数据的独立版本快照。现有模板和CLI是录入底座，不是任意城市全自动搜索承诺。

L5工程下一步：

1. 在页面配置真实模型并提交一次滨江商品调研应用任务，保存本次 Gate、耗时、usage 和返修记录。若失败，优先修复真实失败点。
2. 对同一任务运行多组角色模型组合，比较交付成功率、成本与耗时，再决定是否需要更复杂的 agent 自主协作。
3. 将商品名称标签升级为真正的研究工具：产品属性、问卷、批量 LLM 人设作答、语义一致性探针、对照与真人校准。现有规则模拟继续作为可解释基线。
4. 补齐符合业务年龄范围的公开人口联合结构，更新统计期并审查缺失数据推断。
5. 只有单页任务闭环稳定后，再增加受容器隔离的仓库修改、依赖安装和服务启动能力。

当前不再以人口评审、完整社会运行时或游戏愿景作为 L5 工程的前置条件。每一项后续扩展仍需要可运行产物与独立证据，不以讨论次数作为进度。
